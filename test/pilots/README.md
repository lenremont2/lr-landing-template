# Парная приёмка харнеса

Нужны Node 24, npm, Git, Chrome/Chromium и Pi с настроенной моделью. Вся предметная информация для заданий находится в `fixtures/`. Страница и названия брендов учебные. Контрольные снимки относятся к локальному `reference.html` при 390×844 и 1440×900.

1. До правки харнеса выполните `npm pack --pack-destination <пустая-папка-базы>`. Запишите SHA-256 архива. Повторите упаковку кандидата в другую папку. Обе версии могут иметь одинаковое имя файла.
2. Из корня репозитория выполните `npm run pilot:prepare -- <полный-путь-к-tgz>` для каждой версии. Команда создаёт семь отдельных проектов в TEMP, ставит зависимости, копирует только исходные материалы соответствующей задачи и фиксирует начальное состояние в Git. Выведенный `PILOT_SUITE` — каталог серии. При выборочном повторе укажите после архива имена задач.
3. Выполните `node test/pilots/run.mjs <серия> <задача>` по одному разу для каждой пары версия/задача. Имена задач указаны ниже. Модель по умолчанию — `openai-codex/gpt-6.1-sol`, уровень рассуждения low. Для другой настроенной модели задайте одинаковый `PILOT_MODEL` в обеих сериях. В Windows можно указать путь к установленному JS-лаунчеру через `PILOT_PI_JS`. Используйте одинаковые версии Pi, зависимости, набор инструментов и среду. Проверьте версии зависимостей в lockfile обеих копий.
4. В результате каждого проекта выполните `npm run quality` и `git status --porcelain`. Для проверки рендера после сборки из репозитория запустите `node test/pilots/verify.mjs <серия> <задача>` для всех задач кроме `direction`. Она сохранит снимки рядом с журналом и проверит сценарии из таблицы. Готовый дизайн, факты и визуальное соответствие оценивает сопровождающий по материалам задания.

| Задача    | Ожидаемая работа                | Проверка результата                                                                                                              |
| --------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| transfer  | Перенос утверждённой композиции | Сравнить оба рендера с контрольными снимками. В DOM пять секций по порядку, один корень, фокус виден, Enter ведёт к стоимости.   |
| direction | Выбор направления по брифу      | В дизайн-заметке есть решение для первого экрана, графики и CTA. Проверить ограничения бренда и отсутствие изменений исходников. |
| phone     | Исправление ввода               | Вставка номера с разделителями даёт 11 цифр, правка в середине сохраняет остальные цифры, очистка даёт пустое поле.              |
| branch    | Исправление переходов           | При возврате в ту же ветку симптом сохранён, после смены на питание в FormData остаётся только применимое значение.              |
| review    | Ревью с сохранением исходников  | Проверить пустой diff, наблюдение о светлом тексте на белом фоне у карточки «Экран», сведения о двух ширинах.                    |
| family    | Структура семейства             | Проверить ссылки из общего раздела и данные двух URL по materials/brands.md. Оценить переиспользование структуры в исходниках.   |
| research  | Проверка утверждения            | Срок обратного звонка соответствует источнику, фиксированный срок ремонта отсутствует. Проверить, что источник назван.           |

Сравните результаты по каждому сценарию. У каждого прогона отдельная сессия с местными скиллами. Время на перенос — 12 минут, на короткую задачу — 6 минут. Ограничение по времени считается неполным прогоном. Параметры, вызовы read, diff, время и токены Pi сохраняются в `results/<задача>/summary.json`. Текстовые чтения через shell можно проверить в журнале сессии. Для ревью отделяйте снимки и диагностические артефакты от правок пользовательских файлов. Сохраняйте исходные числа и причину каждого спорного исхода.

Если короткая задача дала разные результаты или отчёт противоречит наблюдению, повторите её ещё дважды на каждой версии в заново подготовленных проектах. Исправление границы скиллов оценивайте по чтениям до первой предметной правки. В выводе о выпуске укажите регрессии, ограничения проверки и результаты пар. Один прогон на запрос даёт наблюдение для этого набора задач. Модельный пилот запускается отдельно от CI.
