# Quiz Generator

Собери короткий сценарий, который уточняет запрос и использует актуальные ответы для результата или заявки. Каждый вопрос должен помогать подбору услуги, расчёту или обработке обращения.

Для переходов и итоговых полей сверь [контракт квиза](../../../docs/landing-kit/forms.md#quiz). Контактный ввод относится к [контракту формы](../../../docs/landing-kit/forms.md#lead-capture).

## Входы

- Цель квиза, проект или исходники, действующие правила и существующий компонент, если он есть.
- Вопросы, варианты, обязательность, зависимости и ожидаемый результат; подтверждённые правила расчёта, если он нужен.
- Формат результата; если предусмотрена заявка — её состав, контактный шаг и контракт атрибутов/полей действующего обработчика. Используй уже принятые данные; выясняй только недостающие решения, влияющие на сценарий.

## Результат

- Квиз в компонентах и файлах проекта; при отправке заявки — интеграция с принятым механизмом.
- Описание шагов в имеющемся формате; если его нет — `docs/quiz.contract.md`: ID вопроса, варианты, условие применимости, переход и ключ в результате/заявке.
- Пример итоговых данных без персональных сведений и отчёт о пройденных путях.

## Порядок работы

1. Проверь существующий квиз и его потребителей. Переиспользуй подходящую реализацию, сверив исходник со стеком, правилами изоляции и передачи данных проекта. Не подключай движок опросов ради простой последовательности шагов.
2. Зафиксируй модель переходов: начальный шаг, условия, доступность «Далее», возврат и завершение. В новом сценарии включай вопросы с понятным назначением; из существующего не удаляй согласованные вопросы без задачи на его пересмотр. Не добавляй ветвление и расчёт цены, если их нет в задаче.
3. Сохраняй ответы при возврате. После изменения раннего ответа пересчитай применимый путь и исключи из итоговых данных ответы потерявших смысл веток. Скрытый из-за пошагового интерфейса вопрос остаётся применимым: его ответ нельзя терять только из-за невидимости.
4. Согласуй прогресс с доступным путём. Если число будущих шагов ещё неизвестно, не обещай фиксированный остаток. Используй устойчивые ID и явное соответствие ответов итоговым данным; при сборе через HTML-форму — реальные поля с `name`/`value`. Исключённые ответы не попадают в результат и отправку.
5. Обеспечь подписи, группы вариантов, видимый фокус и переход фокуса при смене шага. Скрытые шаги не получают фокус и не мешают проверке текущего шага; перед завершением проверь весь применимый путь. Возврат не требует заполнения нового ответа.
6. Если меняется контактный шаг, используй [form-formatter](../form-formatter/SKILL.md) для полей и валидации. По исходникам и разметке проверь, что «Далее»/«Назад» и Enter на промежуточных шагах не отправляют заявку. Проверь итоговые поля без отправки.

## Критерии готовности

- Для нового квиза проверены переходы каждой заданной ветви; для правки — изменённые переходы, их зависимые шаги и основной путь. Необязательно перебирать все комбинации независимых ответов. Нет недостижимых обязательных шагов, тупиков и непредусмотренных циклов.
- Возврат сохраняет применимые ответы; изменение раннего ответа исключает из локального результата и полей для обработчика только устаревшие зависимые значения.
- Обязательные ответы проверяются в нужный момент. Клавиатура, мобильная прокрутка и фокус позволяют пройти сценарий.
- Промежуточные действия не связаны с отправителем по контракту; итоговые поля содержат применимые ответы и контакт без дублей.
- Расчёт воспроизводит предоставленные правила; ограничения оценки видны посетителю. Проверка заканчивается на локальном результате или заполненном контактном шаге, без отправки.

## Если результат неполный

При нехватке правил ветвления, расчёта или атрибутов подключения обозначь пробел и реализуй независимые шаги. Укажи, какие пути удалось пройти в браузере.

Для `lead-quiz-v1` проверь «Назад» из выбора канала и формы, смену ответа и повторное открытие. Сохраняй техническое `value` при изменении подписи. В финальной форме сверяй актуальные `quiz_answer` и `contact_method`.
