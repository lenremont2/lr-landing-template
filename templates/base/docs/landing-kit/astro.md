# Проект на Astro

## Задача и исходные материалы

Результат работы — одностраничный статический Astro-лендинг. В разработку входят исходники, локальный запуск, сборка, проверка в браузере и подготовка к [переносу в Gutenberg](embedding.md). Публикация, REST-запросы, загрузка медиа в WordPress, ключи, темы, плагины и изготовление папки `lr-wordpress` требуют отдельной задачи.

При расхождении источников используй следующий порядок.

1. Последнее указание пользователя.
2. Утверждённое ТЗ и план.
3. Согласованные тексты, цены, контакты и другие факты.
4. Дизайн-референсы, изображения и схемы взаимодействия.
5. Технический справочник Landing Kit.
6. Локальная документация.
7. Существующий код и аналогичные LR-проекты.

Зафиксируй существенное противоречие. Уточни выбор, если он меняет результат. Для неподтверждённых цен, сроков, гарантий, адресов, лицензий и отзывов отметь пробел или используй явно обозначенный заполнитель.

## Каркас и локальный запуск

- В `package.json` и lock-файле проверь версии и доступные команды. Осмотри рабочее дерево, нужные секции, стили, скрипты и материалы брифа. Сохрани пользовательские изменения.
- Один проект содержит один лендинг. В `src/pages/index.astro` задай порядок секций. Общая оболочка живёт в `src/layouts/LandingLayout.astro`, самостоятельные секции — в `src/components/sections/`, повторяемые элементы — в `src/components/ui/`.
- Повторяющиеся карточки, тарифы, FAQ и этапы выводи из массивов. Заводи `src/data/`, когда появятся сами данные. Одноразовую простую разметку можно оставить в секции.
- Стили собираются в `src/styles/landing.scss`, поведение — в `src/scripts/landing.js`. Проектные файлы медиа храни в `public/media/`.
- Перед запуском проверь, работает ли сервер проекта. Если нужен новый, запусти его в фоне и запиши URL и порт. При наличии поддержки в установленной версии Astro используй `astro dev --background`, `astro dev status`, `astro dev logs` и `astro dev stop`. После проверки останови созданный сервер, если он больше не нужен.
- Для архитектурного вопроса используй актуальный `.graphify/graph.json`, если он уже есть. После значимых изменений обнови его штатной командой проекта.

Для существенной правки задай проверяемый результат и доведи одну секцию или пользовательский сценарий до [приёмки](verification.md#verification). Используй существующие компоненты и зависимости, адаптируя их к контенту страницы.

## Архитектура Astro

- Используй статический режим Astro.
- Не используй SSR, API routes, middleware и серверные действия.
- Не рассчитывай на Astro runtime после сборки.
- Не подключай React, Vue, Svelte или другой UI-фреймворк без прямой необходимости и согласования.
- Не создавай client-side islands только ради простого интерактива.
- Для интерактива предпочитай vanilla JavaScript.
- Не используй Tailwind CSS.
- Не используй Bootstrap.
- Не используй глобальные normalize/reset-библиотеки.
- Не добавляй CMS, state manager или компонентный фреймворк «на будущее».
- Соблюдай закреплённую проектом версию Node.js, Astro и lock-файл.
- Не обновляй зависимости без связи с задачей.

Astro-компонентность здесь означает разделение шаблона на поддерживаемые части. Она не означает обязательную гидратацию браузерным фреймворком.
