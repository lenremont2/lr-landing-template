# Как развивать инструкции и роли Landing Kit

В [исходном обсуждении](https://chatgpt.com/share/6b05898d-cc5c-83eb-b496-88f908a9c9e7) предложены два уровня работы. На уровне проекта важны короткая точка входа, документы по назначению и загрузка нужного скилла под задачу. При делегировании важны ответственность исполнителя, границы действий и результат, который другой участник сможет проверить.

В Landing Kit первый уровень уже работает. В пилоте 0.3.1 обе версии прошли семь задач и каждый раз выбрали ожидаемый ведущий скилл. При более узком выборе материалов счётчик токенов Pi снизился на 14,3%, суммарное время выросло на 22,5%. Это наблюдение по одной паре прогонов каждой задачи. Для решения о субагентах нужен отдельный эксперимент. [Условия и результаты](../test/pilots/RESULTS.md)

## Где вносить изменение

Ограничения генератора живут в [правилах репозитория](../AGENTS.md), причины архитектурного выбора — в [ADR](adr/).

Если агент выбирает неверный скилл, проверь [маршрут](../templates/base/.agents/workflows/landing.md) и описания соседних скиллов. Если выбор верный, но пропущен важный шаг, исправь [сам скилл](../templates/base/.agents/skills/). Общий технический контракт держи в [справочнике](../templates/base/docs/MASTER_DEVELOPMENT_PROMPT.md).

Если теряется результат при делегировании, уточни [поручение и обязанности роли](../templates/base/.agents/roles/team.md). Настройки отдельного запуска в Codex находятся в [профиле проверяющего](../templates/base/.codex/agents/landing_reviewer.toml). Изменив инструкцию, выбери [пилот](../test/pilots/README.md), который различит прежнее и ожидаемое поведение.

Шаблон поставляет роли при `create`. Маршрут, скиллы, документ ролей и профиль Codex принадлежат созданному проекту. Для действующего лендинга сравни эти файлы с чистым проектом нужной версии и перенеси подходящие изменения с учётом местных правил.

## Как написать скилл, который легко применить

Пиши для исполнителя, у которого уже есть конкретный запрос. В `description` назови ситуацию, по которой он узнает свою задачу. В теле начни с первого решения: какой компонент открыть, какой путь воспроизвести или какой факт подтвердить. Дай ссылку на подробный контракт в том месте, где он понадобится.

Выбирай форму по работе. Для выбора между скиллами опиши узнаваемые запросы. Для зависимых действий дай короткие шаги в порядке выполнения. Заголовок «Проверь значение после вставки» помогает найти проверку быстрее, чем «Критерии качества». Таблицу оставь для сопоставления данных, например ширин и размеров. Инструкцию должно быть удобно читать сверху вниз и на узком экране.

Например, вместо «Обеспечь корректную обработку состояний квиза» напиши: «Выбери симптом, вернись и смени услугу. В итоговой форме должен исчезнуть ключ прежнего симптома». Тот же пример показывает границу с соседним скиллом: вставка телефона в этом квизе относится к полю формы.

Такой подход виден у Мэтта Покока: `tdd` объясняет решение на конкретном наблюдаемом поведении и отсылает к примерам, а `diagnosing-bugs` выстраивает зависимые действия вокруг воспроизведения сбоя. В руководстве для читателей он отдельно разбирает момент выбора скилла и признаки результата. ## Первый эксперимент с делегированием

Возьми сценарий `branch` из пилотов. На одинаковом исходном проекте сравни работу одного агента с работой исполнителя и независимого проверяющего. Сохрани запрос, модель, настройки и общий бюджет. В обоих вариантах используй один внешний критерий из пилота — состояние ответов при возврате и после смены услуги. Отдельно оцени, обнаружил ли проверяющий реальный дефект, дал ли ложное замечание, сколько времени и токенов заняла вся задача. Если результаты расходятся, повтори на чистых копиях по методике пилота. Запиши наблюдение, решение и ограничение в результатах эксперимента.

Если ошибка воспроизводится, меняй ближайший к причине элемент и повторяй исходный и соседний сценарии. Например, неверный срок ремонта в тексте требует сверки с источником. Сбой выбора исследовательского скилла при таком запросе требует проверки маршрута. Так один случай можно исправить на странице и отдельно установить, есть ли основания менять весь комплект.

## Кандидаты в кастомные скиллы

Рабочие названия для обсуждения. Перед добавлением проверь, можно ли покрыть задачу уточнением существующего скилла.

- **`lr-price-table`** — сверить строки, единицы и условия с утверждённым прайсом, когда бриф уже готов.
- **`lr-offer-evidence`** — сопоставить обещания готовой страницы с источниками и перечислить расхождения. Выделить, если регулярно не хватает landing-research.
- **`lr-reference-review`** — находить расхождения между рендером и принятым макетом на заданных ширинах. Выделить из project-ui при повторяющемся специализированном ревью.
- **`lr-harness-eval`** — сравнить две версии инструкции на одном задании и дать сопровождающему вывод по результатам.
